## 1. Тестлэх функц ба анхны туршилт

Энэ лабораторид оюутан хичээлд бүртгүүлэх `POST /registrations` функцийг шалгав. Тестийг бэлтгэхдээ уг функцийг сонгож, үр дүнд нөлөөлөх оролтуудыг тодорхойлсон. Дараа нь оролт бүрийг ангилж төлөөлөх утгууд сонгосон. Тэдгээрийг хослуулж хүлээгдэх үр дүнтэй спецификаци бичээд, спецификаци бүрийг collection-д ажиллах тест болгосон.

Эхлээд `PUT /students/B231234567` хүсэлтээр `CS201` үзсэн идэвхтэй оюутан, `PUT /courses/CS313` хүсэлтээр `CS201`-ийг урьдач нөхцөл болгосон хичээл үүсгэв. Хоёр хүсэлт тус бүр `200`, `result: "OK"` буцаасан. Дараа нь оюутныг `CS313`-д бүртгүүлэхэд `201`, `result: "OK"` ирснийг хоёр тусдаа `pm.test` шалгалтаар баталгаажуулсан. Бүх локал хүсэлтийн URL-д `{{baseUrl}}` ашигласан бөгөөд түүний утга `http://localhost:3000` юм.

## 2. Тестийн дизайн

### Оролтын сонголт ба төлөөлөх утга

| Сонголт | Эквивалент анги | Төлөөлөх утга |
| --- | --- | --- |
| `studentID`-ийн хүчинтэй байдал | Идэвхтэй, идэвхгүй, байхгүй | `status: "active"`, `status: "inactive"`, үүсгээгүй оюутны ID |
| Оюутны үзсэн хичээл | Урьдач нөхцөлийг хангана, хангахгүй | Хичээл `CS201`, `CS202` шаардвал `coursesTaken: ["CS201", "CS202"]` хангана. `["CS201"]`, `[]` хангахгүй |
| `courseID`-ийн хүчинтэй байдал | Байгаа, байхгүй | PUT-аар үүсгэсэн хичээлийн ID, үүсгээгүй хичээлийн ID |
| Урьдач хичээлийн хамрагдалт | Бүгдийг үзсэн, огт үзээгүй, заримыг үзсэн, урьдачгүй | `prerequisites: ["CS201", "CS202"]`-тай үед `coursesTaken` нь харгалзан `["CS201", "CS202"]`, `[]`, `["CS201"]`. Урьдачгүй үед `prerequisites: []` |
| Хүсэлтийн формат | Хоёр ID байгаа, талбар дутуу, JSON буруу | Хоёр ID-тай JSON, зөвхөн `studentID`-тай JSON, хаагдаагүй JSON объект |

### Тестийн спецификаци

Ердийн амжилттай замаас эхлээд үндсэн дөрвөн алдааг тус бүр шалгахаар сонгов. Давхар алдааны хоёр кейсээр сервер аль алдааг түрүүлж буцаахыг, хязгаарын хоёр кейсээр хоосон жагсаалт болон дутуу талбарыг хэрхэн боловсруулахыг шалгасан.

| ID | Төрөл | Бэлтгэсэн өгөгдөл ба POST хүсэлт | Хүлээгдэх HTTP | Хүлээгдэх `result` | Нэмэлт шалгалт |
| --- | --- | --- | ---: | --- | --- |
| C01 | Амжилттай зам | Идэвхтэй `B231234567` оюутан `CS201` үзсэн. `CS313` нь `CS201` шаарддаг. | 201 | `OK` | `registrationID` нь тоо |
| C02 | Оюутан байхгүй | Хичээлийг үүсгээд бүртгэлийн хүсэлтэд үүсгээгүй оюутны ID өгнө. | 200 | `ERROR_NO_STUDENT` | |
| C03 | Оюутан идэвхгүй | Оюутан идэвхгүй, урьдач хичээлээ үзсэн. Сонгосон хичээл байгаа. | 200 | `ERROR_INACTIVE_STUDENT` | |
| C04 | Хичээл байхгүй | Идэвхтэй оюутан үүсгээд бүртгэлийн хүсэлтэд үүсгээгүй хичээлийн ID өгнө. | 200 | `ERROR_NO_COURSE` | |
| C05 | Урьдач хичээл дутуу | Идэвхтэй оюутан зөвхөн `CS201` үзсэн. Хичээл `CS201`, `CS202` шаарддаг. | 200 | `ERROR_PREREQUISITES` | `missing` массив яг `["CS202"]` |
| C06 | Давхар алдаа | Идэвхгүй оюутныг үүсгээд байхгүй хичээлд бүртгүүлэх хүсэлт илгээнэ. | 200 | `ERROR_INACTIVE_STUDENT` | Идэвхгүй төлөвийн алдаа түрүүлж буцна |
| C07 | Давхар алдаа | Идэвхгүй оюутны `coursesTaken: []`. Хичээл `CS201`, `CS202` шаарддаг. | 200 | `ERROR_INACTIVE_STUDENT` | Идэвхгүй төлөвийн алдаа түрүүлж буцна |
| C08 | Хязгаарын тохиолдол | Идэвхтэй оюутны `coursesTaken: []`, хичээлийн `prerequisites: []`. | 201 | `OK` | `registrationID` нь тоо |
| C09 | Хязгаарын тохиолдол | Идэвхтэй оюутан болон хичээл үүсгэнэ. POST хүсэлтэд зөвхөн `studentID` өгнө. | 400 | `ERROR_BAD_REQUEST` | |

## 3. Collection ба тестийн бие даасан байдал

`lab05-collection.json` дахь C01–C09 хавтас тус бүрт тухайн кейсийн PUT бэлтгэл, бүртгэлийн POST хүсэлт, хариу шалгах oracle-уудыг байрлуулсан. PUT бүрийн хариуг `200` ба `OK` гэж шалгасан. Харин POST бүр дээр хүснэгтэд заасан HTTP статус болон `result`-ийг тусдаа `pm.test`-ээр шалгасан. Байхгүй байх ёстой оюутан, хичээлд тусгай ID сонгож, тэдгээр ID-г аль ч кейсийн PUT хүсэлтээр үүсгээгүй.

Сервер өгөгдлөө санах ойд хадгалдаг. PUT хүсэлт бичлэгийг дахин үүсгэх буюу шинэчилдэг, харин бүртгэл нэмэгдэх бүрд `registrationID` өсдөг. Иймээс C01, C08 дээр `registrationID` тоон утгатай эсэхийг шалгасан. Кейс бүрийг цэвэр асаасан сервер дээр дангаар нь ажиллуулахад бүгд тэнцсэн. Мөн нэг сервер дээр бүх багцыг дараалан хоёр удаа ажиллуулахад хоёуланд нь PASS гарсан. Буруу JSON илгээхэд `400 ERROR_BAD_JSON` буцсаныг collection-оос тусдаа богино шалгалтаар баталгаажуулсан.

## 4. Newman-аар ажиллуулсан үр дүн

Үндсэн багцад **9 кейс, 24 хүсэлт, 51 assertion** ажилласан. Тайлангийн тестийн тоо болох **51** нь PASS логийн `assertions executed`-тэй таарна.

| Ажиллуулалт ба бүтэн лог | Iterations (ажилласан / унасан) | Requests (ажилласан / унасан) | Assertions (ажилласан / унасан) | Newman exit code |
| --- | ---: | ---: | ---: | ---: |
| [PASS](results/newman-pass.txt) | 1 / 0 | 24 / 0 | 51 / 0 | 0 |
| [FAIL](results/newman-fail.txt) | 1 / 0 | 24 / 0 | 51 / 1 | 1 |
| [DOWN](results/newman-down.txt) | 1 / 0 | 24 / 24 | 51 / 51 | 1 |

PASS үед сервер ажиллаж байсан бөгөөд үндсэн collection-ийн бүх шалгалт тэнцсэн. FAIL ажиллуулалтад зориулж `lab05-collection-fail.json` тусад нь бэлдэж, C01-ийн POST дээр зөвхөн статусын хүлээлтийг `201`-ээс `200` болгож өөрчилсөн. Сервер бодитоор `201` өгсөн тул тэр шалгалт унасан. DOWN ажиллуулалтын өмнө серверийг унтраагаад үндсэн collection-ийг дахин ажиллуулахад хүсэлт бүр `ECONNREFUSED` өгсөн.

FAIL үед серверийн өгсөн хариу oracle-ийн хүлээлттэй зөрсөн бол DOWN үед сервертэй холбогдож чадаагүй учраас шалгах хариу ирээгүй. Иймээс DOWN логт хүсэлт болон түүнээс хамаарах assertion-ууд хоёулаа унасан гэж бүртгэгдсэн. CI-д Newman-ийн exit code `0` байвал дараагийн шат руу шилжинэ, `1` байвал шалгалт амжилтгүй гэж үзнэ.

### Үр дүнг дахин гаргах

Репозиторийн үндсэн хавтсаас `lab5/` руу орж серверээ асаана. WSL дээр Newman хэрэгтэй бол `npm install -g newman@6` командаар суулгана.

```bash
cd lab5
node server.js
```

Postman-д `lab05-collection.json`-ийг импортлоод Runner-аас бүтэн багц эсвэл тухайн кейсийн хавтсыг сонгоно. Ингэснээр POST хүсэлтийн өмнө шаардлагатай PUT хүсэлтүүд ажиллана. Newman ашиглахдаа өөр Bash терминалд `lab5/` хавтсаас PASS, FAIL-ийг дарааллаар ажиллуулна.

```bash
mkdir -p results
newman run lab05-collection.json --color off 2>&1 | tee results/newman-pass.txt
echo "exit=${PIPESTATUS[0]}"
newman run lab05-collection-fail.json --color off 2>&1 | tee results/newman-fail.txt
echo "exit=${PIPESTATUS[0]}"
```

DOWN шалгалтын өмнө сервер ажиллаж буй терминалд `Ctrl+C` дарна.

```bash
newman run lab05-collection.json --color off 2>&1 | tee results/newman-down.txt
echo "exit=${PIPESTATUS[0]}"
```

`tee` нь гаралтыг файлд хадгална. Pipeline дуусмагц `${PIPESTATUS[0]}`-оос Newman-ийн кодыг авна. Bash-ийн ердийн тохиргоонд `$?` нь pipeline-ийн сүүлчийн команд болох `tee`-ийн кодыг өгдөг. Логуудыг шинээр үүсгэсэн бол хүснэгтийн тоо болон exit code-ийг мөн тулгаж шинэчилнэ.

## 5. Нэмэлт ажил

### Нийтийн API

`newman run lab05-public-api.postman_collection.json` командаар JSONPlaceholder-ийн `GET /users` хүсэлтийг шалгав. HTTP статус `200`, хариу JSON массив, эхний хэрэглэгчийн нэр `Leanne Graham` гэсэн гурван шалгалт бүгд тэнцсэн. GET хүсэлтэд урьдчилж өгөгдөл үүсгэх хэрэггүй учраас локал API-ийн PUT, POST дарааллыг бэлтгэхээс хялбар байв. [JSONPlaceholder-ийн жишээ хариу](https://jsonplaceholder.typicode.com/users)

### AI-ийн саналтай харьцуулсан нь

> Энэ API-гийн POST /registrations функцийн сонголтуудыг тодорхойлж, сонголт бүрийг эквивалент ангид хуваагаад, ангиудын хослолоор Postman тестүүд үүсгэ.

`server.js`-д тулгуурласан AI-ийн саналд хүсэлтийн формат, оюутан, хичээл болон урьдач нөхцөл гэсэн оролтууд багтсан. Урьдач хичээлүүдийн хувьд бүгдийг үзсэн, дор хаяж нэгийг үзээгүй гэж ангилсан тул огт үзээгүй болон заримыг үзсэн хоёр утгыг тусад нь сонгоогүй. Үндсэн дизайнд энэ хоёрыг хоосон `coursesTaken` болон хэсэгчилсэн жагсаалтаар төлөөлүүлсэн. AI нь `studentID` талбар дутуу хүсэлт, мөн оюутан ба хичээл хоёулаа байхгүй хослолыг нэмж санал болгосон. Эдгээр нь үндсэн C01–C09 дотор тусдаа кейс болоогүй нөхцөлүүд байв. Санал болгосон `400 ERROR_BAD_REQUEST`, `200 ERROR_NO_STUDENT` хүлээлтүүд `server.js`-ийн шалгалтын дараалалтай таарсан. Амжилттай хариунд `201`, `OK`, тоон `registrationID` шалгах санал давтан ажиллуулахад тохирсон.

## Дүгнэлт

Тестийн дизайны таван алхмаас төлөөлөх утгуудаа хослуулж спецификаци гаргах хэсэг надад хамгийн их бодол шаардсан. Жишээлбэл, оюутан байхгүй бол түүний идэвхтэй эсэх, ямар хичээл үзсэнийг тодорхойлох боломжгүй. Хичээл байхгүй үед ч урьдач нөхцөл хангагдсан эсэхийг авч үзэх боломжгүй. C06 болон C07-оор давхар алдаа өгөхөд сервер эхлээд оюутны идэвхийг шалгадгийг ажигласан. C05-ийн хариунаас `missing` массивд зөвхөн үзээгүй хичээл орсныг баталгаажуулсан. C08 дээр үзсэн болон шаардах хичээлийн жагсаалт хоосон байхад бүртгэл амжилттай болсон. Кейс тус бүрийг цэвэр сервер дээр салгаж ажиллуулахад бэлтгэсэн өгөгдөл нь хүрэлцэж байв. Хамруулсан нөхцөлүүдэд API-ийн согог илрээгүй. Санаатай өөрчилсөн статусын шалгалт болон унтраасан сервер хоёрын гаралтыг харьцуулахад асуудал хариуны утгад гарсан уу, эсвэл холболтын шатанд гарсан уу гэдгийг ялгаж болох нь харагдсан.
