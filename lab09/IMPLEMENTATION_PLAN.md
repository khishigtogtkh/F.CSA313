# Лаборатори №9 — JaCoCo ажлын төлөвлөгөө

Эх сурвалж: `Lab09 - Код хамралт JaCoCo (2026).docx`, starter-ийн `pom.xml`, `ScholarshipCalculator.java`, хэрэглэгчийн өгсөн багшийн Лаб 8-ын дүгнэлт болон Лаб 9-ийн сануулга.

Эцсийн сонголт: үндсэн A–D шаардлагууд, одоогийн F.CSA313 репо; нэмэлт gate/CI/AI харьцуулалт хийхгүй. Хэрэгжүүлэлтийн бодит төлөвийг starter/README.md-ээс харна. Доорх түүхэн төлөвлөгөөний тусдаа репо бүтэц нь хэрэглэгчийн эцсийн сонголтоор хүчингүй: root-оос mvn -f lab09/starter/pom.xml verify ажиллуулна. CFG-г гараар зурах болон Teams-ийн бодит илгээлт үлдсэн.

## 1. Одоогийн бүтэц ба ажлын хүрээ

- Maven төсөл `lab09/starter/` дотор байна. Командуудыг энэ хавтсаас ажиллуулна.
- Үндсэн код: `src/main/java/mn/edu/must/sqat/ScholarshipCalculator.java`.
- Үүсгэх тест: `src/test/java/mn/edu/must/sqat/ScholarshipCalculatorTest.java`.
- Starter нь Java release 17, JUnit Jupiter 5.10.2, Surefire 3.2.5, JaCoCo 0.8.12 ашиглаж байна. `prepare-agent`, `verify` үе шатны `report` тохиргоо бий.
- Одоогоор тест, README, results байхгүй. Гадна хавтсанд багшийн DOCX, `__MACOSX/`, `*:Zone.Identifier` байна; эдгээрийг илгээх репод оруулахгүй.
- `letterGrade()`-ийн `score > 60` нь спецификацийн 60–69.99 → D дүрмийг зөрчсөн. A/B/C үед өөрчлөхгүй; D хэсэгт эхлээд унасан тестийн нотолгоо гаргаад засна.
- Хэрэглэгчийн эцсийн сонголтоор одоогийн public `F.CSA313` репозиторийн `lab09/starter/` дотор байрлана. Одоогийн хичээлийн репогийн бусад лаборатори, өөрчлөлтөд хүрэхгүй. Git үйлдэл бүрийн өмнө аль репод ажиллаж байгааг шалгана; бэлтгэлийн үед дур мэдэн nested repository үүсгэхгүй.

## 2. Бэлтгэл ба орчны нотолгоо

1. `git status`, одоогийн branch, remote, default branch болон байгаа файлуудыг шалгах. Хамааралгүй өөрчлөлтүүдийг хадгалах.
2. Оюутны бодит нэр, кодыг тодруулах. README-д загварын нэр, өнцөг хаалт, `PASTE_VERSIONS_HERE` үлдээхгүй.
3. `java -version 2>&1`, `mvn -version 2>&1` ажиллуулж бүтэн бодит гаралтыг README-ийн эхэнд хадгалах. Хуучин лабораторийн хувилбарын мэдээллийг дахин ашиглахгүй.
4. `git config user.name`, `git config user.email`-ийг шалгах; `Your Name`, `Таны нэр` зэрэг загвар байвал бодит тохиргоо хэрэгтэй. Хувийн мэдээллийг таамгаар нөхөхгүй.
5. Илгээх төслийн `.gitignore`-д `target/`, `.idea/`, `.DS_Store`, `__MACOSX/`, `*:Zone.Identifier`, багшийн `*.docx`-ыг хасах дүрэм оруулах. Ignore нэмэхээс өмнө tracked болсон файл байвал зөвхөн тухайн файлыг index-ээс гаргах; эх файлуудыг дур мэдэн устгахгүй.
6. Тестгүй starter дээр `mvn verify` ажиллуулж суурь төлөвийг шалгах. `No tests to run`, `Skipping JaCoCo execution due to missing execution data file` хэвийн; энэ үед тайлан байхгүйг алдаа гэж үзэхгүй. Бодит build алдаа гарвал эхлээд түүнийг оношлох.

Лог авах бүрд Bash дээр `set -o pipefail` хэрэглэнэ. `tee` амжилттай болсон нь Maven амжилттай болсон гэсэн үг биш; Maven-ийн үр дүн, логийн төгсгөлийг давхар шалгана. Логийг засварлахгүй, UTF-8-аар хадгална. Тестийн метод, parameterized display name-ийг латин үсгээр өгнө.

## 4. Хэсэг B — CFG ба Line/Branch 100%

### 4.1 scholarship()-ийн CFG

CFG-г оюутан цаасан дээр эсвэл draw.io/Excalidraw-д **гараар** зурж `cfg.png` болгоно. Энэ төлөвлөгөөний хүснэгт нь гараар зурах CFG-г орлохгүй.

- Лекц 9-ийн тэмдэглэгээг ашиглаж entry, exit, шийдвэр, exception, return зангилаа болон чиглэлтэй ирмэгүүдийг дугаарлах.
- Эхний `||`-ийн `gpa < 0`, `gpa > 4`, `credits < 0` болон хоёр `&&`-ийн нөхцөлүүдийг short-circuit дарааллаар тусдаа шийдвэр болгон илэрхийлэх.
- `hasViolation`, `gpa >= 3.0`, `return 0/50/70/100`, exception замуудыг бүрэн харуулах.
- Ирмэг бүрд тэр замыг дайрсан **бодит тестийн методын яг нэрийг** бичих. Нэг ирмэг олон тесттэй байж болно. Нэр солигдвол зурагтай хамт засах.
- Эхлээд A-ийн тестүүдийг зурагт буулгаад хоосон ирмэгүүдээс B-ийн тестүүдийн жагсаалтыг гаргах. Эцэст нь exception-оос exit хүртэлх ирмэгийг ч нэргүй үлдээхгүй.

### 4.2 Нэмэх тестийн матриц

| Функц/зам | Оролтын жишээ | Хүлээгдэх үр дүн / зорилго |
|---|---|---|
| letterGrade-ийн C, D, F | `75`, `65`, `50` | `C`, `D`, `F`; зааг 60-ыг одоохондоо хэрэглэхгүй |
| Онооны доод, дээд хязгаарын зөрчил | `-1`, `101` | Тус тус `assertThrows(IllegalArgumentException.class, ...)` |
| gpa null, хоосон | `null`, `[]` | Тусдаа нэртэй exception тестүүд; C үед мөн дахин ашиглана |
| gpa switch-ийн бүх case/default | `[95,85,75,65,50]` | `2.0`; A/B/C/D болон F default салаа |
| scholarship invalidGpaBelowZero | `-0.1,16,false` | Эхний OR нөхцөлийн true, exception |
| scholarship invalidGpaAboveFour | `4.1,16,false` | Хоёр дахь OR нөхцөлийн true, exception |
| scholarship invalidNegativeCredits | `3.9,-1,false` | Гурав дахь OR нөхцөлийн true, exception |
| scholarship сахилгын зөрчил | `3.9,16,true` | `0` |
| Өндөр голч, 15 хүрэхгүй кредит | `3.9,14,false` | `70`; эхний AND-ийн голч true, кредит false |

| Голч 3-аас бага | `2.9,16,false` | `0`; сүүлчийн if-ийн false |

A-ийн тестүүдтэй хамт нөхцөл бүрийн true/false замыг шалгана. `gpa`-ийн for давталтын оролт/гаралт, switch default-ийг тайлангаас батална. Exception-уудыг нэг ерөнхий тестийн нэрийн цаана нуухгүй; ялангуяа scholarship-ийн гурван хүчингүй оролт тусдаа тест байна.

```bash

mvn verify 2>&1 | tee results/mvn-verify-B.txt
cp target/site/jacoco/jacoco.csv results/jacoco-B.csv
```

- CSV-ийн `ScholarshipCalculator` мөрөнд `BRANCH_MISSED = 0`, `LINE_MISSED = 0` болох хүртэл үлдсэн замыг HTML-ээс оношилж нэмэх.
- Зааврын 40/41 анхааруулга гарвал OR-ийн гурван true, AND-ийн кредит false зам, F default-ийг эхэлж шалгах. 41 гэсэн тоог урьдчилан үр дүн мэт бичихгүй.

## 6. Хэсэг D — улаан тест → тусдаа засвар → эцсийн ногоон

### 6.1 Алдааг илрүүлэх

Production кодыг өөрчлөхөөс **өмнө** дараах 7 заагийн тохиолдлыг тест болгоно:

| score | expected |
|---|---|
| `60` | `D` |
| `59.99` | `F` |
| `69.99` | `D` |
| `0` | `F` |
| `100` | `A` |
| `89.99` | `B` |
| `90` | `A` |

`letterGradeReturnsDAt60` гэх тодорхой нэртэй тест ашиглаж, логт аль тест унасныг таних боломжтой болгоно.

```bash
set -o pipefail
mvn test 2>&1 | tee results/mvn-test-D-fail.txt
```

- Энд nonzero exit / `BUILD FAILURE` нь хүлээгдэж буй нотолгоо. Логт бодит тестийн нэр, `expected: <D> but was: <F>` утга байгаа эсэхийг шалгах.
- Санаатай заагийн алдаанаас өөр failure байвал түүнийг тусад нь оношлох. Хиймлээр лог бичихгүй.
- Унасан тестийн дараах `mvn verify` нь report шатанд хүрэхгүй. Хуучин HTML/CSV-г шинэ амжилттай хэмжилт гэж ашиглахгүй.
- Унасан тестүүд ба fail логийг `Expose letterGrade boundary defect at score 60` гэсэн тусдаа commit-оор хадгалахыг зөвлөж байна. Энэ нь засварын өмнөх бодит түүхийг харуулна.

### 6.2 Засвар ба final нотолгоо

- Спецификацитай харьцуулж `if (score > 60)`-ыг `if (score >= 60)` болгох. Өөр дүрэм, API-г өөрчлөхгүй.

cp target/site/jacoco/jacoco.csv results/jacoco-final.csv

- README-д fail логоос бодит тестийн нэр, assertion мөрийг оруулах. Засварын commit hash-ийг бодит commit үүссэний дараа бичих; шаардлагатай бол README-ийн лавлагааг дараагийн documentation commit-д нэмэх.
- Гол дүгнэлтийг **4–6 өгүүлбэрээр** бичих: `>` ба `>=` ижил салааны бүтэцтэй; B-ийн оролтууд хоёр талыг дайрсан ч яг 60-ыг шалгаагүй; заагийн тест oracle-той харьцуулж алдааг илрүүлсэн; хамралт кодын гүйцэтгэлийг хэмждэг, спецификацийн зөв/бүх оролтын зөвийг баталдаггүй; бүтцийн ба зааг утгын тестийг хослуулах шаардлагыг тайлбарлах.
